# s2isp — 项目计划

## 1. 目标

> **让 2011–2017 年 Apple Mac 内置的 Broadcom S2 FaceTime HD 摄像头（PCI `14e4:1570`）
> 在 Linux 上工作，且最终产物中不包含任何 Apple 二进制、不包含任何第三方驱��代码。**

分解成两个可独立交付的产物：

| 产物 | 说明 |
|---|---|
| **自研 ISP 固件** (`fw/`) | ARM 二进制，运行在芯片的 ISP 处理器上。替代 Apple 的 `firmware.bin`。 |
| **自研主机驱动** (`driver/`) | Linux 内核模块。替代 [patjak/facetimehd](https://github.com/patjak/facetimehd)。 |

## 2. 非目标

- 不追求兼容 Apple 的 410 条 CISP 命令全集，只实现出图所需的子集
- 不追求与 Apple 画质逐像素一致；目标是**正确可用**
- 不支持 1570 以外的其它 S2 变种（除非顺带就能支持）
- 不做多摄像头 / 多通道并发

---

## 3. 成功标准

全部满足才算完成。每条都必须是**二值可判定**的。

| # | 标准 | 判定方式 | 阈值 |
|---|---|---|---|
| **S1** | 自研固件 + 自研驱动从干净 checkout 可构建 | `make all` 退出码 | 0，且无第三方源码引用 |
| **S2** | 固件加载后完成握手 | 驱动日志出现自研固件发布的通道表与 magic | 通道数 ≥ 1，magic 值匹配 |
| **S3** | 取得传感器原始帧 | 抓一帧 RAW，统计像素分布 | 非全黑/全白，方差 > 阈值，帧尺寸符合传感器输出 |
| **S4** | 输出可用图像 | 抓一帧 YUV 解码为图，人工 + 自动双重判定 | 自动：动态范围 > 50、饱和度 > 0.15；人工：可辨识场景 |
| **S5** | 曝光可控且 AE 收敛 | 改曝光时间，亮度单调变化；AE 模式下亮度收敛 | 单调性 100%；收敛误差 < 15% |
| **S6** | 产物无外部依赖 | 对发布 tarball 做二进制/源码审计 | Apple 二进制 0 个；第三方驱动代码 0 行 |
| **S7** | 可复现 | 全新 clone → 文档命令 → 摄像头工作 | 从零到出图 ≤ 1 小时 |

### S6 的审计方式（客观，不靠声明）

```
# Apple 二进制：无 .bin/.dat/未剥离 ELF，且无已知 Apple kext 哈希
sha256sum <所有文件> | grep -f apple-firmware.sha256        # 必须 0 命中

# 第三方驱动代码：无 patjak/facetimehd 的特征符号
grep -rnE 'fthd_|facetimehd|FTHD_' driver/ fw/               # 必须 0 命中
```

## 4. 验证协议

每个里程碑都必须有一个**可执行的检查脚本**，而不是人工判断。

```
tools/check.sh <milestone>    # 跑该里程碑的全部判定，返回 0/1
```

设计原则：
- **客观优先** —— 能用数字判定的绝不用眼睛
- **真机** —— 所有验证都在这台 2013 rMBP 上跑
- **可重复** —— 每次判定前重新加载模块、清 dmesg，避免状态污染

## 5. 里程碑与闸门

每个里程碑有明确的**交付物**和**闸门条件**。闸门不通过就停下来重新评估，
不带着未解决的问题往后走。

### M0 — 工具链与规格（进行中）

| | |
|---|---|
| 交付物 | ARM 交叉工具链；固件分析工具（反汇编/命令表提取/寄存器访问追踪）；`docs/` 下的协议规格 |
| 验证 | `tools/check.sh m0`：能从固件镜像中自动提取出命令表并生成规格文档 |
| 闸门 | **命令表自动提取成功，且提取结果与固件运行时自报的 opcode 一致** |

现状：已完成大半。命令名表已定位（镜像偏移 `0x0b22f0`，411 项 `{name_ptr, id}`），
已确认 `wire_opcode = id − 1`，并用固件自身的调试输出交叉验证。

### M1 ★ 自研固件启动 — **项目分水岭**

| | |
|---|---|
| 交付物 | 一个 ARM 固件：能被主机加载 → 报告 1 个 IPC 通道 → 发布通道描述表 → 响应 ping 命令 |
| 验证 | `tools/check.sh m1`：加载自研固件后，主机观察到正确的握手序列 |
| 闸门 | **握手成功**。若不成立，判定"ISP 启动协议存在我们尚未发现的硬件依赖"，回到评估 |

这一关的意义：如果自研固件能让主机完成握手，后续就是常规工程；
如果不行，说明还有我们没看到的硬件约束，需要重新评估整个方案。

## 6. 风险与终止条件

诚实列出可能让项目失败的原因，以及对应的应对。

| 风险 | 影响 | 应对 / 终止条件 |
|---|---|---|
| ISP 启动协议有我们没识别的硬件依赖 | M1 卡住 | 3 轮尝试仍不通 → 停止，重新评估是否存在绕过 ISP 的硬件通路 |
| S2 的 ISP 处理单元无法绕过，必须复刻完整算法 | 工作量从月级变成年级 | 优先验证"只下发系数、像素运算在硬件里"的假设（见 §7） |
| 传感器型号差异大 | M3 泛化难 | 先只支持本机这一颗（1871），其它型号后置 |
| 真机只有一台 | 回归测试受限 | 固件/驱动都做成可回滚，先建立"能跑"的基线再改 |

**明确的终止条件**：若 M1 在 3 轮独立尝试后仍无法握手，
则本项目**不成立**，应转向「编写我们自己的 ISP 固件在别的平台上验证」或「仅重写主机驱动、
固件仍用 Apple 的」这两条退路。

## 7. 已知的关键假设（需逐一验证）

| # | 假设 | 怎么验 | 在哪验 |
|---|---|---|---|
| A1 | ISP 固件是 ARM 代码 | 反汇编入口是 ARMv7 启动序列 | ✅ 已验证 |
| A2 | 像素级处理在定功能硬件里，固件只下发系数 | 命令集里大量 `*_COEFF_SET` / `*_MATRIX_SET` / `*_WEIGHT_SET` | 部分验证（命令集分析） |
| A3 | 命令表即协议真值 | 固件运行时打印的 opcode 与表推导值一致 | ✅ 已验证 |
| A4 | 主机侧硬件 bring-up 可独立重做 | DDR PHY 标定在驱动侧完成 | 推断，待 M2 验证 |
| A5 | 采集通路可绕开 ISP 的部分算法 | 需 M3 验证 | 待验 |

**A2 是整个项目最关键的假设**，它决定了我们是要复刻一整套 ISP 算法，
还是只需写一个"配置 + 调度"固件。M1/M3 的实验设计都以验证 A2 为目的。

## 9. 工作方式上的自我约束

1. **不复制他人代码。** 所有实现从零编写。已有驱动只作为"协议行为参考"，
   且其结论都要用**运行时观测**独立复核后才采信。
2. **区分「知识」与「代码」。** 从 Apple 固件里读出的协议结构是关于硬件接口的知识；
   我们的实现必须是自己的。固件里的 ARM 机器码不会被复制 —— 我们写自己的固件。
3. **每个结论都要能被复现。** 结论写在 `notes/`，附上产生它的命令。
4. **不确定就说不确定。** 宁可标注"待验证"，不要写成结论。
